# 심평원 비급여 가격 수집 기록

## 1. 문제와 기존 방식의 한계

서비스는 건강보험심사평가원(HIRA)이 공개한 의료기관별 비급여 가격을 검색·비교한다. 비급여는 건강보험이 적용되지 않아 환자가 전액 또는 대부분을 부담하는 진료·검사·치료 항목이다.

처음에는 기관을 하나씩 찾은 뒤, 각 기관의 `비급여항목병원목록상세` API(Application Programming Interface, 프로그램이 데이터를 주고받는 창구)를 순서대로 호출했다. 기관 사이에 1초 대기를 두고, 오류 때 최대 5회 재시도했다. 강남구만도 기관 수가 3천 곳 이상이어서 하루 동안 약 9%밖에 진행되지 않았다.

이 방식의 한계는 다음과 같다.

- 기관 수만큼 API를 호출하므로 지역이 커질수록 시간이 급격히 늘어난다.
- 심평원 API는 시간 초과와 서버 자원 부족 오류가 있어 재시도가 잦다.
- 상세 API를 한 페이지(100건)만 읽던 기존 구현은 항목이 100개를 넘는 기관의 나머지 항목을 놓칠 위험이 있다.
- 수집 중단에 대비한 체크포인트(checkpoint, 중단 뒤 이어 하기 위한 저장 지점)는 있었지만, 느린 호출 방식 자체를 해결하지는 못했다.

## 2. 해결책을 찾고 검증한 방법

CSV(표 형식 파일) 일괄 다운로드 가능 여부를 공식 심평원·공공데이터포털에서 조사했지만, 전국 기관별 가격 전체를 바로 받는 공식 CSV는 찾지 못했다. 대신 같은 공식 서비스의 `비급여항목병원목록요약` API를 확인했다.

실제 API 응답을 시험했다.

1. 강남구 코드 `sgguCd=110001`로 가격 요약 API를 호출했다.
2. 가격 3,229건이 1,000건 단위 4페이지로 반환되는지 확인했다.
3. 병원기본목록 API에서 기관명·주소·위도·경도를 3,162건, 4페이지로 확인했다.
4. 두 자료에 공통으로 있는 `ykiho`(심평원이 암호화해 제공하는 기관 식별값)로 연결할 수 있음을 검증했다.

따라서 기관별 상세 호출 대신, 가격 요약 API와 병원기본목록 API를 각각 페이지 단위로 수집해 결합하는 방식으로 바꿨다. 가격 자료에는 지도용 위치 정보가 부족하고, 병원기본정보에는 가격이 없기 때문에 두 자료를 함께 사용한다.

## 3. 전국 수집 결과

수집일: 2026-08-25. 실제 수집은 약 2시간 38분이 걸렸다.

- 가격 요약 API: 187,132건, 188페이지
- 병원기본목록 API: 79,802건, 80페이지
- 최종 가격 레코드: 187,132건
- 가격을 신고한 기관: 3,959곳
- 포함 시군구: 250곳
- 기관 정보 조인 누락, 필수값 누락, 완전히 같은 레코드 중복: 모두 0건

기관 기본정보 수가 더 큰 것은 정상이다. 모든 기관이 공개 대상 비급여 가격을 신고하는 것은 아니며, 가격 레코드가 없다고 가격이 무료이거나 진료를 하지 않는다는 뜻은 아니다. 한 기관의 여러 비급여 항목은 같은 `ykiho`를 공유하므로, `ykiho`가 반복된다는 이유만으로 삭제하면 안 된다.

API 응답은 1,000건씩 저장했다. 오류가 나면 HTTP 실패, JSON 형식 오류, `resultCode` 비정상, 시간 초과 문자열을 확인하고 3초 간격으로 최대 5회 재시도했다. 모든 페이지가 API의 전체 건수와 일치하고 기관 연결 누락이 없을 때만 최종 데이터를 바꿨다.

데이터가 약 75MB라 TypeScript 배열로 직접 넣으면 컴파일러가 처리하기 어렵다. 최종 데이터는 JSON(JavaScript Object Notation, 가벼운 데이터 저장 형식)으로 저장하고 TypeScript 파일은 이를 읽어 앱에 전달한다.

## 4. 작업 분담과 운영 방식

이번 작업은 판단이 필요한 일과 반복 실행을 분리해 진행했다.

| 구분 | Codex 담당 | opencode 담당 |
| --- | --- | --- |
| 조사·설계 | 공식 데이터 경로 조사, API 의미 검증, 호출 수와 위험 판단 | 없음 |
| 구현 검토 | 데이터 형식, 체크포인트, 오류 처리, 검증 기준 검토 | 정해진 범위의 수집기 구현 보조 |
| 장시간 실행 | 진행 기준·중단 기준 결정, 상태 확인 | 페이지별 API 호출, 재시도, 체크포인트 저장, 재개 실행 |
| 최종 반영 | 결과 검증, 테스트, Git 커밋, 사용자 요청 시 push·배포 | 결과와 로그 보고 |

운영 순서는 다음과 같다.

1. Codex가 수집 대상, 공식 출처, 성공 기준과 금지 사항을 짧은 작업지시서로 확정한다.
2. opencode는 그 지시서 범위 안에서 반복 수집만 수행한다. 수집 중 임의로 데이터 구조를 바꾸거나 Git commit·push를 하지 않는다.
3. Codex는 매 페이지 로그 대신 체크포인트 수, 마지막 갱신 시각, 오류 수처럼 짧은 상태만 확인해 토큰 사용을 줄인다.
4. 완료 뒤 Codex가 전체 건수, 조인 누락, 중복, 타입 검사와 테스트를 검증한 뒤 필요한 데이터만 커밋한다.

이 방식의 핵심은 하청 작업을 단순 실행으로 제한하고, 데이터 품질·배포·Git 이력처럼 되돌리기 어려운 결정은 Codex가 끝까지 책임지는 것이다. 같은 데이터 파일을 쓰는 수집기는 동시에 실행하지 않는다.

## 5. 이후 수집 전 체크리스트

1. **먼저 일괄 경로를 찾는다.** 기관별 상세 API를 반복 호출하기 전에 공식 CSV, 파일데이터, 요약 API, 지역 필터, 대량 다운로드 가능 여부를 확인한다.
2. **작은 표본으로 API 의미를 검증한다.** 지역 코드, 전체 건수, 페이지 수, 필수 필드, 필터가 실제로 적용되는지를 1~2페이지로 시험한다. `ykiho` 단독 조회처럼 전체 건수가 조건과 다르게 나오는 API도 있으므로, 조건별 결과를 비교한다.
3. **호출 수를 계산한다.** `전체 건수 / 페이지 크기`로 API 호출 수와 예상 시간을 먼저 산정한다. 수천 번의 직렬 호출이 예상되면 설계를 다시 검토한다.
4. **재개 가능하게 만든다.** 페이지별 체크포인트, 오류 재시도, 마지막 갱신 시각을 둔다. 한 페이지라도 실패했을 때 부분 데이터로 서비스 파일을 덮어쓰지 않는다.
5. **데이터 결합 규칙을 먼저 정한다.** 공통 식별값, 주소·좌표 누락 기준, 정상 중복과 실제 중복의 구분을 수집 전에 문서화한다.
6. **운영 비용도 함께 본다.** 대형 파일은 GitHub·Vercel 배포와 검색 속도에 영향을 준다. 데이터가 커지면 지역·항목별 인덱스(index, 빠른 찾기용 목차), 캐시(cache, 자주 쓰는 결과를 잠시 저장하는 기능), 데이터베이스 또는 객체 저장소(object storage, 큰 파일 보관 서비스)를 검토한다.

## 6. 검색 성능과 다음 개선 방향

전국 데이터 이후 검색이 느려진 이유는 요청마다 약 18만 행을 읽고 처음부터 필터링하기 때문이다. 항목 목록도 매 요청마다 전체 데이터를 훑어 다시 만든다.

우선 항목 목록과 시군구·항목별 인덱스를 수집 시점에 미리 생성해야 한다. 검색 시 전체 파일을 순회하지 않고 필요한 지역·항목 데이터만 읽도록 바꾸고, 자주 쓰는 검색 결과에는 캐시를 적용한다. 화면의 로딩 표시만 바꾸는 것으로는 근본적인 속도 문제가 해결되지 않는다.
