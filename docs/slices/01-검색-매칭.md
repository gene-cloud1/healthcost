# Slice 01 — 검색어를 공식 항목명으로 매칭하기

> **기준 문서**: PLAN_simple.md 기능 목록의 1번
> ("독감주사"를 검색하면 공식 항목명으로 자동 매칭)을 이번 슬라이스로 씁니다.
> PLAN.md의 Task 1(React+Vite 전환)·Task 5(TypeScript 서버리스 함수)는
> PLAN_simple.md에 없는 내용이라, 이번 슬라이스는 오늘 검증된 vanilla JS
> 구조를 그대로 유지하는 걸 전제로 썼어요.

## 목표 (한 문장)
사용자가 검색창에 "독감주사"처럼 편한 말로 입력하면, 화면에 공식 항목명
("인플루엔자 예방접종료")이 매칭되어 표시된다.

## 사용자 시나리오
- 검색창에 "독감주사" 입력 → 검색 → "인플루엔자 예방접종료"로 매칭됐다는 안내가 뜬다
- "독감 예방접종", "독감백신" 등 다른 표현을 입력해도 같은 항목으로 매칭된다
- 등록되지 않은 말(예: "감기약")을 입력하면, 에러 없이 "매칭 실패" 안내가 뜬다

## 입력 / 출력
- **입력**: 검색창에 입력한 자유 텍스트 (한글, 공백 포함 가능)
- **출력**: 매칭된 공식 항목명 1개 (또는 매칭 실패 안내 문구)

## 데이터 흐름 (오늘 스켈레톤 검증 결과 기준)
1. 브라우저에서 검색어를 `/api/*` 엔드포인트로 전달
2. 서버리스 함수가 "공식 항목명 ↔ 구어체 표현" 매핑 목록을 검사해 일치하는 항목을 찾음
3. 매칭 결과(공식 항목명 또는 "없음")를 JSON으로 응답
4. 브라우저가 응답을 받아 화면에 표시

오늘 스켈레톤(`api/items.js`)으로 "브라우저 → 서버리스 함수 → 브라우저" 왕복
자체는 production에서 이미 검증됨. 이번 슬라이스는 그 왕복 구조를
"매칭 로직"으로 바꿔 채우는 작업.

## 실제 현재 파일 구조 (스켈레톤 배포 후 확인된 사실)
```
healthcost/
├── index.html       ← vanilla HTML/JS (React 아님, 입력+저장+목록 스켈레톤)
├── api/items.js     ← CommonJS 서버리스 함수, 더미 인메모리 저장소
├── server.js        ← Day1 스텁, 로컬 전용, 프로덕션에서는 안 쓰임
├── package.json     ← 의존성 없음 (React/Vite/TypeScript 전부 없음)
└── .vercel/         ← Framework Preset "Other"로 확정 (오늘 수정)
```
- `PLAN.md`, `lib/`, `data/`, `scripts/`, `src/`는 **이 브랜치(=현재 production)에
  존재하지 않음** — 다른 세션의 로컬 main(origin에 push 안 된 4커밋)에만 있음
- `.env.local` / `HIRA_API_KEY`도 이 브랜치엔 없음

## 이번 슬라이스에서 만들 것 (파일명·역할만, 코드 아님)
- 공식 항목명 ↔ 구어체 표현 매핑 데이터 — **임시 하드코딩 표** (예:
  `{공식항목명, 별칭 목록}` 형태 배열 몇 개). PRD의 pgvector 임베딩 검색이
  나중에 이 자리를 대체할 예정이라, 지금은 이걸 갈아끼우기 쉽게만 만들면
  되고 그 이상으로 정교하게 안 만듦
- 매칭 요청을 처리하는 서버리스 함수 (`api/items.js`를 대체하거나 새 엔드포인트 추가 — 형식 미정)
- 검색창 + 매칭 결과 표시 UI (기존 `index.html`을 확장하는 것으로 가정)

## 완료 조건
- [ ] 배포된 URL에서 "독감주사" 검색 → "인플루엔자 예방접종료" 문구가 화면에 뜬다
- [ ] "독감 예방접종", "독감백신" 등 동의어도 같은 결과로 매칭된다
- [ ] 등록 안 된 검색어 입력 시 에러 화면 없이 안내 문구가 뜬다

## 이번 슬라이스에서 안 하는 것
- 실제 병원 가격 비교/표시 (슬라이스 2 이후)
- 거리순 정렬, 위치 정보 사용
- HIRA 공공데이터 API 실호출 (매핑 테이블만 있으면 됨 — "물어볼 것 4번" 확인 필요)
- React/Vite 전환 (하려면 "물어볼 것 2번"에서 결정)
- 스켈레톤의 더미 저장 기능(`api/items.js`의 입력→저장→목록) 유지 여부

## PLAN.md와 달라진 부분
1. **기준 문서를 PLAN_simple.md로 바꿈**: PLAN.md는 Task 1(React+Vite 전환)
   → Task 5(TypeScript 서버리스 함수) 순서를 전제로 하는데, 오늘은
   PLAN_simple.md 기준으로 vanilla JS 구조를 유지한 채 기능부터 만들기로
   했어요. React+Vite 전환, TypeScript 전환은 이번 슬라이스에 포함 안 함.
2. **시작점 자체가 다름**: PLAN.md Task 1은 "Day1 `<h1>` 스텁"에서
   출발한다고 가정했는데, 지금 production은 이미 vanilla JS +
   `/api/*.js` 서버리스 함수 패턴이 실제로 동작하는 걸 검증한 상태예요.
3. **Vercel Framework Preset 버그**: PLAN.md엔 없던 문제인데, 프로젝트
   설정이 "Node.js"로 잘못 잡혀 있어서 `/api/*`가 전부 무시되고 있었어요.
   오늘 "Other"로 고쳤어요 (PLAN.md에 없던 새 사실).
4. **다른 세션의 작업과 히스토리 분기**: PLAN.md·`lib/`·`data/`·`scripts/`가
   들어있는 다른 세션의 로컬 main(4커밋, React+Vite+TS 기반)이 origin에
   안 올라간 상태에서, 오늘 이 브랜치가 origin/main을 앞질러 버렸어요.
   그 4커밋은 이제 origin과 히스토리가 갈라져서 그대로는 병합이 안 되고,
   애초에 스택 방향(React+TS vs vanilla)도 이번 슬라이스와 달라요.
5. **HIRA_API_KEY 미설정 확인**: PLAN.md Task 4는 이 키가 있다고 가정했는데,
   이 브랜치는 물론 다른 세션 쪽 커밋 메시지("stops safely without
   HIRA_API_KEY")를 봐도 실제로는 아직 키가 세팅된 적이 없어요. (이번
   슬라이스는 매핑 테이블만 있으면 돼서 이 키가 필요 없다고 가정했어요.)

## 결정된 사항 (답변 반영)
1. **매핑 데이터** = 임베딩 도입 전까지만 쓸 임시 하드코딩 표. 나중에
   pgvector 임베딩 검색으로 교체될 자리라, 지금은 갈아끼우기 쉬운 정도로만
   단순하게 둠 (형식은 구현 시 정함: 배열 vs JSON 파일 — 사소한 선택이라
   구현하면서 결정)
2. **다른 세션(React+Vite+TS, PLAN.md 기반)**: 이번 세션은 별도로 진행,
   당분간 안 건드림. MVP 완성 시점에 merge/통합 예정
3. **스켈레톤의 더미 입력→저장→목록 기능**: 지금 결정 안 함. 이후 슬라이스
   스펙을 보고 필요 여부 판단해서 그때 정리
4. **파일명**: `docs/slices/01-검색-매칭.md`로 확정
